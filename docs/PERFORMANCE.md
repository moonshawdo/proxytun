# proxytun 性能

本文给出 proxytun 的性能测试方法、结果和分析。基准程序在 [crates/proxytun/tests/bench.rs](../crates/proxytun/tests/bench.rs),可以复现。

## 结论

- **吞吐**:经 TUN 捕获的单连接下载约 **1.1 GB/s**,是同一个客户端直接经同一代理下载的约 55%;主机端口转发约 1.2 GB/s。
  这是本机回环上、代理不构成瓶颈时的上限，真实代理和网络通常远低于它，不会碰到。
- **瓶颈在 tun 线程**:命名空间里的 TCP 处理落在写 TUN 的那个线程上，单连接吞吐受它限制;它的时间约九成在内核态。
  试过 TUN 校验和卸载，只快约 10%,没有合入(4.8)。
- **建连**:每条新连接比客户端自己做 SOCKS5 握手多约 **0.5 ms**。
- **假 DNS**:顺序查询约 4500 次/秒(每次往返约 0.22 ms)。
- **启动**:`proxytun -- true` 约 90 ms(建命名空间、TUN、见证进程)。

## 1. 测试环境

| 项 | 值 |
|---|---|
| CPU | Intel Core i5-8265U(4 核 8 线程,1.6 GHz) |
| 内存 | 11 GiB |
| 系统 | WSL2,内核 6.18 |
| 构建 | `cargo test --release`(`opt-level = 3`、thin LTO、`codegen-units = 1`) |
| 客户端 | curl 8.5.0、Python 3.12 |
| proxytun | user namespace 模式，默认日志级别(info),日志输出到 `/dev/null` |

## 2. 测试方法

源站和 SOCKS5 代理都是测试进程自己的线程(256 KiB 缓冲),所有流量都在本机回环上，测到的是客户端一侧的开销。
每项都与"不经 proxytun、同一个客户端做同样的事"对比:

| 测试 | 经 proxytun | 对照 |
|---|---|---|
| `throughput`:经 TUN 下载 | `proxytun --proxy socks5://代理 -- curl http://bench.test/bytes/1073741824`(1 GiB) | `curl --socks5-hostname 代理 http://bench.test/bytes/1073741824`(curl 自己连代理) |
| `throughput`:主机端口转发 | `proxytun --proxy socks5://代理 -- curl http://127.0.0.1:源站端口/bytes/1073741824`(源站在主机上监听，被转发进命名空间) | `curl http://127.0.0.1:源站端口/bytes/1073741824` |
| `connection_setup`:建连 | Python 顺序发 1000 次 HTTP 请求，每次新连接(域名只解析一次) | 同一个 Python 脚本，每次新连接先自己做 SOCKS5 握手 |
| `fake_dns`:假 DNS | Python 在命名空间里顺序发 20000 次 A 查询，每次一个新域名 | 无(假 DNS 只在 proxytun 里有) |
| `start_and_exit`:启动 | `proxytun --proxy ... -- true` 的总耗时 | 无 |

下载、建连、假 DNS 每项跑 3 轮，启动跑 10 次，取中位数，括号里是最小 ~ 最大。运行方式(需要 curl 和 python3):

```bash
cargo test --release --test bench -- --ignored --nocapture --test-threads=1
```

## 3. 结果

### 3.1 吞吐(1 GiB 单连接下载,MB/s)

| 路径 | proxytun | 不经 proxytun | 比例 |
|---|---|---|---|
| 经 TUN 捕获，经 SOCKS5 代理 | **1131**(1122 ~ 1143) | 2047(2035 ~ 2122) | 55% |
| 主机端口转发 | **1194**(1068 ~ 1272) | 4062(2766 ~ 4146) | 29% |

### 3.2 建连(1000 次顺序短连接，每次的毫秒数)

| | 每次 |
|---|---|
| proxytun | **1.885**(1.864 ~ 1.892) |
| 客户端自己做 SOCKS5 握手 | 1.352(1.314 ~ 1.382) |
| 额外开销 | **约 0.53 ms** |

### 3.3 假 DNS 与启动

| 测试 | 结果 |
|---|---|
| 20000 次顺序 A 查询 | **4476 次/秒**(3993 ~ 4721),每次往返约 0.22 ms |
| `proxytun --proxy ... -- true`(10 次) | **87.6 ms**(71.8 ~ 116.5) |

## 4. 分析

### 4.1 吞吐的上限在 tun 线程

经 TUN 的连接比直接连代理多走一段：程序 → 命名空间内核 → TUN → tun 线程改写 → 写回 TUN → 内核 → 捕获监听 → 中继 → 代理。
其中命名空间里的 TCP 处理(收包、确认、窗口)都发生在 tun 线程 `write` 的调用里，这个单线程就是瓶颈(下载时名为 `tun` 的线程约占 95% 的 CPU,`top -H` 可见)。
按 `/proc/<pid>/task/<tid>/stat` 的 utime / stime 拆开，下载时 tun 线程用户态约 8%、内核态约 88%:proxytun 自己的包解析与改写只占一小部分，
时间主要花在 `read` / `write` 系统调用里，即内核把每个约 64 KB 的包拷出、再拷回，并在这个线程里完成命名空间那条 TCP 连接的协议栈处理。
所以 proxytun 的单连接上限约 1 GB/s,与代理的速度无关。

这个上限只有在本机回环、代理不构成瓶颈时才碰得到;经真实网络的代理通常远低于它，所以没有做多队列 TUN 等优化(第 5 节)。

### 4.2 主机端口转发

主机端口转发不经 TUN 的地址改写，但多一次中继拷贝:命名空间里的监听 socket → proxytun → 主机上的服务。回环上直连约 4 GB/s,
经 proxytun 约 1.2 GB/s,对本地服务(数据库、开发服务器)足够。

### 4.3 为什么不用零拷贝(splice)

proxyhook 的中继两端都是普通 socket,`splice(2)` 收益明显;proxytun 实现时对比过(同一台机器,2 GiB 下载):

| 路径 | splice | 普通拷贝(64 KiB 缓冲) | 不经 proxytun |
|---|---|---|---|
| 经 TUN 捕获的连接 | 约 800 MB/s | 约 1070 MB/s | 约 2100 MB/s |
| 主机端口转发 | 约 2700 MB/s | 约 1350 MB/s | 约 4100 MB/s |

经 TUN 的路径上，普通拷贝快 20–30%:瓶颈本来就在写 TUN 的线程,splice 的管道操作只会加重它。主机端口转发上 splice 快一倍，
但 1.35 GB/s 对本地服务已经足够，为它单独保留 splice 不值得。

### 4.4 中继缓冲大小

每条中继连接每个方向 64 KiB 缓冲(一建立就占 128 KiB)。实现时经 TUN 下载 3 GB 的对比:64 KiB 约 990 MB/s,32 KiB 约 915(−8%),
16 KiB 约 750(−24%),8 KiB 约 545(−45%)。按"吞吐下降不超过 5%"的标准保留 64 KiB;同时中继的连接最多 8192 条，缓冲最多约 1 GiB。

### 4.5 每条连接的开销

约 0.5 ms 的额外开销来自：命名空间里多一次 TCP 握手(程序 ↔ 捕获监听，经 tun 线程改写)、accept、查改写表与假 IP 池、规则判定，
以及默认 info 级别每条连接两行日志。连接是被代理一侧的往返主导的，真实环境里这 0.5 ms 通常可以忽略。

### 4.6 规模上限

| 项 | 上限 | 依据 |
|---|---|---|
| 持续新建连接 | 约每秒 1.37 万条 | 地址改写表约 103 万个键，关闭的连接保留 75 秒 |
| 同时中继的连接 | 8192 条(fd 上限低时更少) | 每条两个 fd、两个 64 KiB 缓冲 |
| 地址改写表内存 | 满表约 200–280 MB | 约 103 万条 |
| 假 IP 映射内存 | 100 万条约 280 MB(超长、含转义字符的域名最坏约 2.3 GB) | 映射上限 100 万条 |
| 改写表清扫 | 每次持锁最多 4096 项(约 1 ms) | 大批同时到期时分批，避免 tun 线程停顿丢包 |

### 4.7 热路径上没有的东西

- tun 线程转发 TCP 数据包时不分配内存、不复制：包解析、地址改写和增量校验和都在读缓冲上原地完成;新连接的 SYN 只在改写表扩容时分配，
  回 RST、回 ICMP 和派发 DNS 查询时也分配。
- 普通数据包只查一次改写表;只有程序的 SYN(新建条目)、监听侧的 SYN-ACK 和双方的 RST 会改变条目。
- 系统文件只在启动或收到信号时读;规则匹配每条连接只转一次小写，后缀匹配不分配内存。
- 会按包频率重复的告警(表满、fd 用尽)限速为每 10 秒一条。

### 4.8 校验和卸载的试验

回环接口不计算 TCP 校验和，而 TUN 默认没有校验和卸载。试过在建 TUN 时加 `IFF_VNET_HDR` 并用 `TUNSETOFFLOAD` 打开 `TUN_F_CSUM`:
每个包前多一个 10 字节的 virtio 头，带 `NEEDS_CSUM` 标志的包只修正伪首部的部分和，转发时原样带上这个头，接收端内核不再校验。
卸载确实生效(命名空间里 `ethtool -k tun0` 显示 `tx-checksumming: on`),端到端测试在 gnu 与 musl 上全部通过。
同一台机器、同一时段，经 TUN 下载 1 GiB(每次 3 轮取中位数):

| 版本 | 各次中位数(MB/s) | 相对不经 proxytun | tun 线程 CPU |
|---|---|---|---|
| 原版 | 1109、1119、1116、1075 | 54% ~ 57% | 96% |
| 校验和卸载 | 1154、1226、1232 | 56% ~ 59% | 94% |

吞吐只提高约 8% ~ 10%,tun 线程仍然跑满：校验和只是它内核态时间里的一小块(4.1)。没有合入：收益小，却让热路径上的每个包都多一层头部处理，
也没有在 CentOS 7 真机上验证过;真实网络和代理的吞吐远到不了这个上限。

## 5. 没有做的优化

| 优化 | 为什么没做 |
|---|---|
| 多队列 TUN | 单个 TUN 收发循环的上限约 1 GB/s,远高于真实代理的吞吐;单条连接也仍只走一个队列 |
| TUN 校验和卸载 | 试过(4.8):只快约 10%,不值得增加的复杂度 |
| 中继用 splice | 见 4.3:经 TUN 的路径反而更慢;主机端口转发上更快，但已经够用 |
| 更小的中继缓冲 | 见 4.4:缩到 32 KiB 吞吐就下降 8% |
